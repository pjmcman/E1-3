# Mini NPU 시뮬레이터 (E1-3)

3×3 ~ 25×25 크기의 필터와 패턴을 **MAC(Multiply-Accumulate) 연산**으로 비교해
패턴이 Cross(+)인지 X인지 판정하는 Python 콘솔 프로그램입니다.

- 실행 파일: `main.py`
- 사용 라이브러리: 표준 라이브러리만 사용 (`json`, `time`)
- Python 3.8 이상

## 구현 요약

### MAC 연산 (`mac`)
같은 위치의 값끼리 곱해 모두 더합니다. N×N이면 곱셈·덧셈을 N²번 하므로 **O(N²)** 입니다.
행 수나 어느 행의 열 수가 다르면 `ValueError`를 발생시켜, 호출하는 쪽에서 크기 불일치를 처리합니다.

### 라벨 정규화 (`normalize_label`)
`data.json`의 라벨은 `"+"`, `"cross"`, `"x"`처럼 표기가 섞여 있습니다.
앞뒤 공백을 지우고 소문자로 바꾼 뒤 아래 표로 표준 라벨에 맞춥니다. 표에 없는 라벨은 `ValueError`로 거르고 해당 항목은 경고와 함께 건너뜁니다.

| 원래 표기 | 표준 라벨 |
|---|---|
| `+`, `cross`, `Cross`, `CROSS` | `Cross` |
| `x`, `X` | `X` |

필터 키(`cross`, `x`)와 패턴의 `expected`(`+`, `x`)에 같은 함수를 쓰므로 두 쪽 라벨이 항상 같은 이름으로 비교됩니다.

### epsilon 동점 처리 (`judge`)
부동소수점 덧셈은 순서에 따라 `0.9`와 `0.8999999999999999`처럼 아주 작은 오차가 생깁니다.
`>`로만 비교하면 이런 오차 때문에 사실상 같은 점수가 한쪽으로 판정되므로,
**두 점수 차이가 `EPSILON = 1e-9`보다 작으면 동점**으로 봅니다.

- 모드 1: 동점이면 `판정 불가`
- 모드 2: 동점이면 `UNDECIDED`로 판정하고, 기대값과 다르므로 **FAIL**로 셉니다.

### 모드 2 실패 처리 (`evaluate_case`)
다음 경우 프로그램을 멈추지 않고 해당 케이스만 FAIL로 기록하고 이유를 출력합니다.

- 패턴 크기에 맞는 필터(`size_N`의 Cross, X)가 없음
- 패턴과 필터의 행/열 수가 다름 (`mac`의 `ValueError`를 받아 처리)
- 두 점수가 동점
- 판정 결과가 기대값과 다름

### 성능 측정 (`measure_mac_ms`)
`time.perf_counter()`로 `mac()` 호출 구간만 `REPEAT = 10`번 재서 1회 평균(ms)을 구합니다. 입력·출력 시간은 포함하지 않습니다.
모드 2의 3×3 행은 `data.json`에 3×3 데이터가 없어서, 비교 기준으로 넣은 `BASELINE_3X3` 행렬로 잽니다.

## 결과 리포트

측정 환경: Windows 11, Python 3.14

### 모드 2 판정 결과

| 케이스 | Cross 점수 | X 점수 | 판정 | 기대 | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL (동점) |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL (동점) |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL (동점) |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

**총 6개 중 통과 3개, 실패 3개.** 실패 3건은 모두 두 점수가 부동소수점 오차 수준(약 1e-15)으로만 다른 경우입니다.
epsilon 없이 `>`로 비교했다면 size_5_1, size_25_1은 Cross, size_13_2는 X로 판정되어 셋 다 **기대값과 반대로** 틀렸을 것입니다.
epsilon 비교는 이런 경우를 "잘못된 판정" 대신 "판정 불가"로 드러내 줍니다.

### 크기별 성능 (MAC 1회 평균, 10회 반복)

| 크기 | 평균 시간(ms) | 연산 횟수(N²) |
|---|---:|---:|
| 3×3 | 0.0032 | 9 |
| 5×5 | 0.0040 | 25 |
| 13×13 | 0.0189 | 169 |
| 25×25 | 0.0738 | 625 |

- 측정값은 실행할 때마다 달라집니다(같은 PC에서도 2배 안팎). 절대값보다 **크기에 따른 증가 추세**를 봐야 합니다.
- 5×5 → 25×25에서 연산 횟수는 25배, 시간은 약 18배 늘어 **대체로 N²에 비례**합니다.
- 3×3, 5×5처럼 작은 크기에서는 함수 호출·반복문 준비 같은 고정 비용 비중이 커서 N² 비율보다 차이가 작게 나옵니다.

## 보너스

### 패턴 생성기 (`generate_pattern`)
`generate_pattern("Cross" | "X", N)`으로 N×N 크기의 Cross 또는 X 행렬을 만듭니다.
가운데 칸이 있어야 모양이 대칭이 되므로 N은 **3 이상의 홀수**만 받습니다(그 외에는 `ValueError`).

- Cross: 가운데 행과 가운데 열이 1
- X: 두 대각선(`i == j`, `i + j == N - 1`)이 1

모드 3에서 3, 5, 13, 25, 51, 101 크기로 패턴과 필터를 만들어 판정해 보면 모두 PASS입니다.
같은 모양끼리는 1인 칸 수만큼 점수가 나오고(**2N − 1**), 다른 모양끼리는 가운데 한 칸만 겹쳐 **1**이 나옵니다.
점수 차이가 크기에 따라 커지므로 data.json과 달리 동점이 생기지 않습니다.

### 2차원 vs 1차원 펼치기 (`flatten`, `mac_1d`)
행렬을 미리 1차원 리스트로 펼쳐 두고, 인덱스 하나로 한 번만 반복하는 `mac_1d`를 2차원 `mac`과 비교했습니다.
펼치기는 측정 전에 한 번만 합니다(NPU가 가중치를 연속 메모리에 미리 배치해 두는 상황을 가정). 두 방식의 점수는 모든 크기에서 같습니다.

| 크기 | 2차원(ms) | 1차원(ms) | 1차원/2차원 |
|---|---:|---:|---:|
| 3×3 | 0.0009 | 0.0004 | 0.48 |
| 5×5 | 0.0019 | 0.0009 | 0.49 |
| 13×13 | 0.0093 | 0.0053 | 0.57 |
| 25×25 | 0.0335 | 0.0206 | 0.61 |
| 51×51 | 0.1250 | 0.0895 | 0.72 |
| 101×101 | 0.5036 | 0.3362 | 0.67 |

(평균/100회, 3번 실행해도 같은 경향. 큰 크기는 실행마다 0.6~0.9 사이로 흔들림)

- **1차원이 모든 크기에서 더 빠릅니다.** 2차원 `mac`은 행마다 안쪽 리스트 꺼내기, 열 수 검사, 안쪽 `range` 생성을 N번 더 합니다.
- **작은 크기일수록 차이가 큽니다(약 2배).** 위의 행 단위 추가 작업은 O(N)이라, 전체 작업 O(N²) 중 차지하는 비율이 N이 작을수록 크기 때문입니다.
  N이 커지면 원소마다 하는 곱셈·덧셈(O(N²))이 대부분을 차지해 두 방식의 차이가 줄어듭니다.
- 두 방식 모두 연산 횟수는 N²으로 같으므로 **시간 복잡도는 둘 다 O(N²)** 입니다. 1차원 펼치기는 복잡도가 아니라 반복마다 드는 고정 비용을 줄입니다.
